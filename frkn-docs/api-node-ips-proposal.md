# Proposal: node_ips — несколько IP-адресов у одной ноды

## Цель

Устойчивость к блокировкам по IP. Нода с несколькими адресами (купили сервер с
5 IP) отдаёт их все одним массивом; клиент подключается к случайному, а при
недоступности перебирает остальные. Все остальные параметры коннекшена
(порты, ключи, reality, junk-параметры) идентичны — меняется только адрес
входа.

## Модель

- У ноды (`node_id`) появляется опциональный список адресов `node_ips`.
- Семантика: **та же нода, другой вход**. Это НЕ несколько нод — один
  `node_id`, один набор ключей, одни порты, один connection. Адрес выбирается
  на клиенте в момент коннекта.
- `hostName` в конфиге остаётся как есть — первичный адрес (= первый элемент
  `node_ips`).

## Изменения API

### 1. `/v1/services` — отдавать `node_ips` в коннекшене (опционально)

```json
{
  "connection_label": "Suomi · AmneziaWG",
  "connection_uuid": "1ac65b82-...",
  "node_id": "7f3c9a01-...",
  "node_ips": ["78.17.28.66", "78.17.28.67", "78.17.28.68"],
  "country_code": "FI",
  "service_protocol": "awg"
}
```

Клиент использует массив для health-check: пингует каждый адрес, бейдж/RTT
сервера = лучший живой адрес. Поля нет → текущее поведение (один адрес).

### 2. `/v1/config` — отдавать `node_ips` в ответе (опционально)

```json
{
  "config": "<gzip+base64, как сейчас>",
  "node_ips": ["78.17.28.66", "78.17.28.67", "78.17.28.68"],
  "api_config": { ... }
}
```

- Внутри самого конфига (INI/JSON в `config`) endpoint/hostName — по-прежнему
  первичный адрес. **Старые клиенты работают без изменений.**
- Новый клиент берёт массив, выбирает адрес сам и подставляет в endpoint
  при подключении.
- Требования к значениям:
  - `node_ips[0]` == hostName/endpoint внутри конфига (консистентность для
    старых клиентов и пингометра);
  - все адреса слушают **те же порты** и обслуживаются **теми же ключами**
    (WG/AWG server_pub_key, reality publicKey/shortId, hysteria2 и т.д.) —
    нода должна быть настроена принимать трафик на всех адресах;
  - порядок не значим (клиент сам перемешивает);
  - поле отсутствует или пустое → один адрес, поведение как сейчас.

Никаких других изменений в `/v1/config` не требуется: `connection_id`,
`node_id`, обмен `public_key` — всё без изменений, выбранный IP на бэк не
отправляется (это чисто клиентский выбор транспортной точки входа).

## Обратная совместимость

- Поле чисто аддитивное: старые клиенты его игнорируют и используют
  `hostName` из конфига.
- Нода без `node_ips` — поведение байт-в-байт как сейчас.
- Миграция: поле можно включать per-нода в любой момент, клиентский рефреш
  конфига подхватит массив автоматически.

## Edge cases

- **Частичная блокировка**: основной сценарий — клиент перебирает массив при
  фейлах коннекта. Бэку ничего делать не надо.
- **Вывод адреса из эксплуатации**: убрать из `node_ips`; клиент получит
  обновлённый массив при очередном рефреше `/v1/config`. Уже сохранённый у
  клиента мёртвый адрес просто проиграет в переборе.
- **Смена всего набора адресов**: то же самое, рефреш подхватывает.
- **health-check**: если `node_ips` есть в `/v1/services`, клиент пробывает
  все адреса; офлайн-адреса исключаются из рандомного выбора до следующего
  прогона.

## Клиентская сторона (наша, после выкатки)

- Храним `node_ips` в конфиге сервера (опциональное поле рядом с hostName).
- На коннект: случайный адрес из массива (приоритет — адресам, живым по
  последнему health-check), подстановка в endpoint/address для WG/AWG/VLESS/
  Hysteria2 в единой точке сборки VPN-конфига.
- Фолбэк: фейл коннекта → следующий адрес из перемешанного пула, пока пул не
  исчерпан; юзерская отмена сбрасывает пул. (Та же механика, что недавно
  сделанный перебор кандидатов в автовыборе.)
- Поля нет → ровно текущее поведение, одна точка входа.
