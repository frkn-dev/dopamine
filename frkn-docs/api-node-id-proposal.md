# Proposal: node_id — адресация конкретной ноды в /v1/services и /v1/config

## Модель данных

- **connection (`connection_id`)** — юзер-специфичные настройки: клиентские
  ключи/UUID, привязка к подписке, протокол. Модель пришла из xray: там для
  коннекта достаточно UUID (вместо email, как в классических панелях).
- **node (`node_id`)** — нода-специфичные настройки: host/IP, порт,
  server_pub_key, reality-параметры (publicKey/shortId/serverName), для
  WG/AWG дополнительно endpoint + junk-параметры (Jc/Jmin/.../H1-H4, I1-I5).
- **Выданный конфиг = join(connection, node)**: клиентская часть из
  connection + транспортная часть ноды. Один и тот же connection на разных
  нодах даёт разные рабочие конфиги с одинаковыми клиентскими ключами.

## Что сломано сейчас

`/v1/services` отдаёт `connections[]`, где у разных нод один и тот же
`connection_uuid`, а `node_id` отсутствует вовсе. Пример из одного ответа
(6 AWG-нод, один uuid `1ac65b82-...`): Suomi, Suomi2, Kazakhstan, Swe,
Netherlands 67, Uncle Sam.

Клиент зовёт `/v1/config` с `connection_id` → получает конфиг одной
(произвольной) ноды на все строки. В приложении все AWG-серверы подписки
оказываются клонами одной ноды. Отличить ноды на клиенте невозможно —
данных для этого в API нет.

## Предлагаемые изменения

### 1. `/v1/services` — отдавать `node_id` в каждом коннекшне

```json
{
  "connection_label": "Suomi · AmneziaWG",
  "connection_uuid": "1ac65b82-...",
  "node_id": "7f3c9a01-...",
  "country_code": "FI",
  "country_name": "FI",
  "env": "production",
  "service_protocol": "awg"
}
```

Требования:
- `node_id` уникален per нода и **стабилен во времени** (клиент кэширует его
  и шлёт при каждом реконнекте/рефреше; смена node_id для той же ноды
  воспринимается как новая нода).
- `connection_uuid` остаётся как есть (юзер-специфика) — обратная
  совместимость.

### 2. `/v1/config` — принимать опциональный `node_id`

- `node_id` передан → вернуть конфиг именно этой ноды (join с connection
  из `connection_id`/auth).
- `node_id` не найден / не принадлежит этому connection → явная ошибка
  (например 404 `node_not_found`), НЕ молча другая нода — клиент по этой
  ошибке перезапросит `/v1/services` и перестроит список.
- `node_id` не передан → текущее поведение (любая нода по
  country+protocol). Задокументировать как «недетерминированный выбор» —
  для старых клиентов.

### 3. Edge cases

- **Смена страны** пользователем: клиент НЕ шлёт `node_id` (нода из другой
  страны — новый выбор), только `connection_id` + `server_country_code`.
- **Нода выведена из эксплуатации**: `/v1/config` с её `node_id` → 404,
  клиент делает re-sync через `/v1/services`.
- **Смена IP ноды**: `node_id` тот же, `/v1/config` возвращает новый IP —
  наш авто-рефреш подхватывает.

## Клиентская сторона (с нашей стороны готово)

- `connection_id` уже шлём при установке, рефреше и реконнекте.
- Как только `node_id` появится в `/v1/services`: сохраняем в конфиг
  сервера и добавляем в payload `/v1/config` — изменение точечное, путь уже
  проложен.
- Ручная проверка ответов: `fetch_frkn_config.py <sub_id> <connection_id>
  <country> <protocol>` (добавим аргумент node_id).
