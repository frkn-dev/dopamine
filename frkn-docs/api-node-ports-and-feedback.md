# ТЗ: `node_ports` (порты на адрес) и `feedback` (сообщение из приложения)

Два независимых куска. Первый — расширение существующего ответа API, второй —
новый тип полезной нагрузки на уже существующем канале отчётов.

---

# 1. `node_ports` — свой порт для каждого адреса пула

## Зачем

Сейчас у ноды один порт на все адреса `node_ips`: клиент подменяет только host,
порт остаётся из конфига. Из-за этого кейс «IP1:443 доступен, IP2:8443 доступен,
а IP1:8443 и IP2:443 провайдер режет» клиент обслужить не может — половина пула
для него бесполезна.

Нужно: у каждого адреса в пуле может быть свой порт.

## Где отдавать

Те же два места, где уже отдаётся `node_ips`:

1. `/v1/services` — в объекте коннекшена;
2. `/v1/config` — рядом с `config`, `node_ips`, `api_config`.

## Формат

```jsonc
{
  "connection_uuid": "1ac65b82-...",
  "node_id": "7f3c9a01-...",
  "node_ips":   ["93.89.220.48", "93.89.220.49", "77.221.152.88"],
  "node_ports": { "93.89.220.48": 443, "93.89.220.49": 8443 },
  "service_protocol": "awg"
}
```

### Правила

- **карта `ip → port`**, а не массив объектов: `node_ips` уже используется
  клиентом (карточка, пробы, сборка пула), порядок и форма ломаться не должны;
- поле **опциональное**; нет поля → клиент берёт порт протокола из контейнера
  (текущее поведение, ничего не меняется);
- ключи **обязаны побайтово совпадать** со строками в `node_ips` (тот же формат
  IPv4, без пробелов и портов вида `1.2.3.4:443`);
- `port` — **число** (не строка), диапазон 1…65535;
- адрес, которого нет в `node_ports`, обслуживается портом протокола — частичная
  карта допустима;
- если порт адреса совпадает с портом протокола — ключ можно не указывать;
- если `node_ports` пришёл, а `node_ips` нет (или пуст) — `node_ports` игнорируется;
- `node_ports` относится к конкретному коннекшену (протоколу). У ноды с
  несколькими протоколами у каждого коннекшена своя карта.

### Валидация на бэкенде

- порт вне 1…65535 или не число → запись **отбрасывается** (не 500), в лог
  предупреждение; остальные записи карты остаются рабочими;
- ключ, отсутствующий в `node_ips` → отбрасывается с предупреждением в лог.

## Что делает клиент (уже реализуемо, ждёт только поле)

1. Порт адреса = `node_ports[ip]`, иначе порт протокола из контейнера.
2. Рукопожатие/проба — каждый адрес проверяется **на своём порту**.
3. При коннекте на альтернативный адрес подменяются **и host, и port** в конфиге.
4. В карточке адрес показывается как `93.89.220.49:8443`, если порты различаются.
5. В отчёте `probe.handshake[]` уже есть поле `port` — там будет реальный порт адреса.

## Приёмка

- нода с `node_ips: [A, B]` и `node_ports: {A: 443, B: 8443}` → клиент
  подключается и к A:443, и к B:8443 (проверяется выключением A в карточке);
- `/v1/config` и `/v1/services` отдают одинаковую карту для одного коннекшена;
- при отсутствии поля поведение не изменилось ни на байт;
- некорректный порт не роняет ответ (проверить на одном битом значении).

# 2. `feedback` — сообщение из приложения

## Зачем

Сейчас «Поддержка» — это `mailto:`-ссылки. На iPhone без настроенной почты юзер
не может ничего отправить и уходит. Нужна отправка текста прямо из приложения,
с приложенным отчётом о подключении.

## Транспорт

**Рекомендуем переиспользовать существующий канал отчётов**, а не заводить
новый эндпойнт:

- `POST /v1/report` (как сейчас, с `auth_data` и `support_tag`);
- `POST /v1/report/scan` — не трогаем.

Требование к бэкенду: **принимать и сохранять лишний ключ `feedback`** в теле
отчёта, не отвечая 4xx. Если гейтвей валидирует тело строго по схеме — schema
надо расширить этим полем.

## Формат

Полный отчёт (юзер поставил «приложить отчёт») — текущее тело плюс блок:

```jsonc
{
  "app": { "version": "4.8.14.79", "platform": "ios", "os": "26.6.2" },
  "at": "2026-10-30T09:20:11Z",
  "support_tag": "023d804b-e677-446e-aba4-d02742fb0e3a",
  "feedback": {
    "feedback_id": "b6c1f0a2-5d3e-4f2a-9a11-7c1f0e2d3b44",
    "message": "На WLESS не подключается, крутит и отваливается",
    "lang": "ru",
    "attach_report": true
  },
  "target": { ... },
  "probe": { ... },
  "session": { ... }
}
```

Только текст (юзер снял галочку) — минимальное тело:

```jsonc
{
  "app": { "version": "4.8.14.79", "platform": "ios", "os": "26.6.2" },
  "at": "2026-10-30T09:20:11Z",
  "support_tag": "023d804b-e677-446e-aba4-d02742fb0e3a",
  "feedback": { "feedback_id": "...", "message": "...", "lang": "ru", "attach_report": false }
}
```

### Правила

- `message` — UTF-8, **1…2000 символов** после trim; пустое сообщение с
  `attach_report: true` допустимо (юзер просто жмёт «отправить отчёт»);
- `feedback_id` — UUID, генерируется клиентом один раз на сообщение.
  **Нужна идемпотентность**: повтор с тем же `feedback_id` не создаёт вторую
  запись (клиент повторяет отправку при отсутствии сети);
- `lang` — `ru` / `en` / `uk` (для маршрутизации к тому, кто читает);
- `attach_report` — bool, дублирует, полное тело пришло или минимальное;
- аккаунт/подписка берутся из `auth_data`, как и сейчас для отчётов.

### Хранение и доставка (на усмотрение бэкенда)

- хранить: `feedback_id` (уникальный индекс), `message`, `lang`,
  `attach_report`, `support_tag`, аккаунт, `app.platform`/`version`,
  серверное `created_at`, полное тело отчёта как есть;
- уведомление команде — по вашему выбору (Telegram-бот / письмо / дашборд);
- ответ клиенту: `200` + `{"ok": true}`; клиент считает доставленным только 2xx.

## Приёмка

- отправка проходит **на устройстве без настроенной почты**;
- текст и `support_tag` видны в хранилище, при `attach_report: true` рядом
  лежит полный отчёт (целевой сервер, handshake, MTU, конфиг-хеш);
- два запроса с одинаковым `feedback_id` → одна запись;
- `message` длиной 2001 символ → 4xx с внятным текстом (клиент обрежет, но
  контракт должен быть явным);
- лишний ключ в теле отчёта без `feedback` не ломает приём (обратная совместимость).

---

## Обратная совместимость

Старые клиенты живут в проде долго, поэтому контракт жёсткий с двух сторон.

### Старый клиент ← новый ответ API

- незнакомые ключи (`node_ports`, веса и пр.) клиент не читает — падений нет;
- порт он берёт из контейнера (`last_config.port` / `containers[].<protocol>.port`),
  то есть ведёт себя ровно как до фичи;
- на адресе с альтернативным портом он не подключится — но и раньше не мог:
  теряется выгода, а не работоспособность.

**Жёсткое требование:** порт протокола в конфиге остаётся **всегда**;
`node_ports` — только переопределение поверх него. Если порт убрать и оставить
его лишь в `node_ports`, старые клиенты пойдут на порт 0 и перестанут
подключаться.

### Новый клиент ← старый ответ API

Нет `node_ports` → берётся порт протокола строки. Поведение идентично
прежнему, фича включается только при наличии поля.

### Тело отчёта

- старые клиенты не шлют `attempts`, `mtu`, `config`, `network`,
  `probe.handshake`, `feedback` — читать как отсутствующие данные, не как ошибку;
- новые клиенты шлют больше ключей, чем старые: валидация должна быть по
  **optional**-полям, неизвестный ключ — в лог, а не 4xx. Иначе любое
  расширение отчёта ломает приём.

### Если понадобится отсечка по версиям

`app.version` и `app.platform` уже есть в каждом отчёте — по ним можно понять
долю клиентов без поддержки `node_ports`, прежде чем менять семантику
`node_ips`.

## Сводка по срокам (для планирования)

| Часть | Кто | Объём |
|---|---|---|
| `node_ports` в `/v1/services` + `/v1/config` | бэкенд | мало: поле в ответе + валидация |
| приём `feedback` в `/v1/report`, идемпотентность | бэкенд | мало: расширить схему + уникальный индекс |
| уведомление команде о фидбеке | бэкенд | по желанию |
| клиент: порты на адрес, коннект, карточка | клиент | ~полдня, готов сразу как поле появится |
| клиент: форма фидбека + очередь повторов | клиент | ~полдня |
