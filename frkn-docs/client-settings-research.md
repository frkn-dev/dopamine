# Клиентские настройки, которые может менять пользователь — рисёрч

Вопрос: что из «чисто клиентских» настроек стоит отдать пользователю. Первые кандидаты —
MTU для WG/AWG и выбор адресов внутри пула. Ниже: что есть в коде сейчас, что можно
сделать, чем это грозит и сколько стоит.

---

## 1. MTU для WG/AWG

### Что сейчас

MTU не задаётся пользователем — он приходит вместе с конфигом и просто доезжает до туннеля:

| Слой | Где | Что делает |
|---|---|---|
| Конфиг протокола | `config_key::mtu` внутри `last_config` / протокольного конфига | значение из API или импорта |
| Дефолты | `protocols::awg::defaultMtu`, `protocols::wireguard::defaultMtu` (`vpnConfigurationController.cpp:110-114`) | подставляются, если в конфиге пусто |
| Desktop | `client/mozilla/localsocketcontroller.cpp:153` → IPC `deviceMTU` | уходит демону |
| Демон | `client/daemon/daemon.cpp:277-281` | `deviceMTU == 0` → **1420** по умолчанию |
| iOS | `client/platforms/ios/ios_controller.mm:737,1005` | берёт `mtu` из конфига, иначе дефолт протокола |
| Android | Go-библиотека туннеля (Kotlin `setMtu` не вызывается) | берёт MTU из WG/AWG-конфига |
| UI | `PageSettingsApiServerInfo.qml:253` → `ApiConfigsController.getCurrentServerMtu()` | **только показывает**, менять нельзя |

### Что можно сделать

Клиентский override: значение в настройках, которое **перекрывает** MTU из конфига в момент
сборки конфига для туннеля (одна точка — там, где формируется `config_key::mtu`).

- Скоуп: глобально (все серверы) + опционально «для этого сервера».
- Диапазон: 1200…1500, шаг 1, дефолт — «как в конфиге» (пустое значение = не перекрываем).
- Валидация на вводе + предупреждение: «слишком большой MTU даёт эффект „половина сайтов не
  открывается“: TCP-хендшейк проходит, крупные пакеты теряются».
- Кнопка «Сбросить к значению сервера».
- Показывать фактическое значение в «Инфо о сервере» рядом с исходным: `1420 (сервер: 1380)`.

### Риски

- **Главный:** неверный MTU не даёт ошибки подключения — получается «подключено, но часть
  сайтов не грузится». Это худший вид баг-репорта (см. известную жалобу про UDP/MTU).
- Пользователь меняет MTU, забывает, потом жалуется через месяц — поэтому значение должно
  быть видно в «Инфо о сервере» и попадать в диагностический отчёт.
- iOS: NE перезапускает туннель при изменении конфига — менять только при выключенном VPN.

### Оценка

**~1 день**: настройка (глобальная + per-server), одно место инъекции, UI-строка с валидацией,
строка в «Инфо о сервере», тест на Windows/Android.

## 2. Выбор адресов внутри пула (галочки)

### Что сейчас

- API отдаёт у сервера массив `node_ips` (`servers_model.cpp:284`), у мульти-IP ноды там все
  адреса; у пула — адреса всех нод пула.
- При подключении `connectToServerIndex()` (`connectionController.cpp:471+`) собирает пул
  пар `(row, ip)` по всем строкам того же пула/протокола/env/подписки, **шафлит** и ходит по
  ним при неудаче (`retryWithNextIp`).
- Пользователь список адресов видит, но не управляет им: `PageSettingsApiServerInfo.qml:323`
  («Available addresses») — только текст.
- Фактически использованный адрес есть в `ConnectionController.currentEndpoint` и в
  телеметрии (`target.address`).

### Что можно сделать

Чекбоксы «какие адреса использовать» на уровне пула:

- Хранить локально: ключ `subscription|pool|protocol|env` → список выключенных IP.
- При сборке пула в `connectToServerIndex()` фильтровать выключенные адреса.
- UI: экран «Адреса» (из карточки сервера / «Инфо о сервере»), список `IP — включён`,
  счётчик «N из M включено», кнопки «Все» / «Сбросить».
- Guard: нельзя выключить **все** — минимум один включённый (иначе непонятная ошибка).
- Новые адреса, пришедшие с обновлением подписки, по умолчанию **включены** (иначе юзер
  молча теряет свежие ноды).
- Показывать, к какому адресу подключились сейчас (уже есть `currentEndpoint`) и в отчёте
  указывать, какие адреса были исключены — чтобы поддержка видела причину.

### Риски

- Юзер выключит живые адреса и будет жаловаться «стало хуже» — нужен сброс в один тап и
  явная подпись «включено 2 из 5».
- Если адрес выключен, а он единственный у ноды — эффект «сервер пропал из пула»; поэтому
  фильтр применяем **после** сборки пула и проверяем, что пул не пуст.
- Поддержка: к отчёту добавляем `pool {total, enabled, disabled[]}` — иначе разбор жалобы
  снова превращается в переписку.

### Оценка

**~1.5 дня**: настройки (ключ на пул), фильтр в сборке пула, экран со списком и чекбоксами,
guard на «все выключены», отражение в «Инфо о сервере» и в телеметрии.

## 3. Что ещё просится в тот же экран (для полноты)

| Настройка | Сейчас | Стоит ли отдавать |
|---|---|---|
| DNS (свой) | частично есть в настройках | уже есть — не дублировать |
| Kill switch (soft/strict) | есть | есть |
| Split tunneling | есть | есть |
| Junk-параметры AWG (I1–I5) | приходят с сервера | **нет**: сломают обфускацию, поддержка не разберёт |
| MTU | только показ | **да** (см. §1) |
| Адреса пула | только показ | **да** (см. §2) |
| Авто-подбор MTU (проба) | нет | отдельная фаза, ~2 дня |

## 4. Рекомендация по фазам

1. **Фаза 1 (1 день): MTU override.** Самый частый «локальный» источник проблем у
   конкретного оператора; реализуется в одной точке и полностью обратимо (сброс).
2. **Фаза 2 (1.5 дня): выбор адресов пула.** Закрывает реальный сценарий «один IP
   заблокирован, остальные работают» без смены сервера и без новых нод.
3. **Фаза 3 (2 дня, отдельно): авто-подбор MTU** — проба 1280/1360/1420/1500 через туннель и
   выбор наибольшего рабочего; требует аккуратной сети проб и не должна пугать пользователя.

## 5. Общее

- Всё это **локальные** настройки: ничего не уходит на сервер, разрешений не требует,
  на сторах ничего не меняет (в отличие от телеметрии).
- Обе настройки обязательно отражать в «Инфо о сервере» и в диагностическом отчёте —
  иначе поддержка не отличит «кривой MTU» от «блока у оператора».
- Менять только при выключенном VPN: на iOS/Android перезапуск туннеля с новым конфигом
  иначе даёт гонку состояний.
