# Proposal: share tokens — шаринг одного коннекшена (`frkn://conn/<token>`)

## Цель

Пользователь делится **одним конкретным подключением** (например «Android Mama
Wireguard»), а не всей подпиской: ссылка `frkn://conn/<token>` импортирует в
приложение получателя ровно один сервер и не даёт доступа ни к чему остальному.

## Проблема сейчас

Единственный credential в API — `subscription_id` (`auth_data.api_key`). Любая
передача его другому человеку даёт полный доступ: все коннекшены подписки,
список девайсов (`/v1/account_info`), управление ими. «Поделиться одним
сервером» сейчас невозможно в принципе — только «отдать ключ от всего
аккаунта».

`connection_uuid` / `node_id` роль credential играть не могут: это не секреты,
а адресация (см. `api-node-id-proposal.md`), и без `api_key` они ничего не
открывают.

## Модель

**Share token** — scoped credential. Ключевое решение: токен указывает не на
коннекшен владельца, а на **дочерний коннекшен**, создаваемый под получателя.

При минте токена бэк создаёт на подписке новый connection: свои UUID/ключи,
та же нода (`node_id`), метка `label` и флаг **`issued_via: "share"`**. Токен
связан с этим дочерним коннекшеном. По сути паттерн `mrkting.short_codes`
(код → подписка), только токен → дочерний коннекшен, и токен сам является
авторизацией для ровно одной операции: получения его конфига.

Зачем дочерний коннекшен, а не ссылка на коннекшен владельца:

- **Настоящий revoke без изменений нод.** Отзыв токена = существующее удаление
  коннекшена целиком (ZMQ delete → нода сносит пир/UUID). Работает одинаково
  для VLESS и WG/AWG, новых сообщений ноде и релиза fnode не требуется.
  Вариант «гасить только перевыдачу» не подходит: уже выданный конфиг
  продолжил бы работать бессрочно — это revoke, который ничего не отзывает.
- Конфиг владельца никогда не страдает (никакой ротации UUID).
- Revoke самоочищается: дочерний коннекшен удаляется, мусор не копится.

Свойства токена:

- Формат: Crockford base32, **16 символов (80 бит)**, хранится слитно,
  отдаётся сгруппированным (`xxxx-xxxx-xxxx-xxxx`). 80 бит, а не 50 как у
  short codes: токен — bearer credential для `/v1/config`, а не только
  публичный резолвер.
- TTL: без срока, живёт до явного revoke. Смерть/просрочка подписки гасит все
  её токены автоматически (конфиг по ним отдаёт стандартный expired-ответ).

## Изменения API

Все эндпоинты — через тот же AGW encrypted envelope, что и остальные `/v1/`.

### 1. `POST /v1/share` — создать токен (владелец)

Auth: обычный `auth_data.api_key` (subscription_id). Тело (расшифрованное):

```json
{
  "auth_data": { "api_key": "<subscription_id>", "id": "<subscription_id>" },
  "connection_uuid": "b023cacd-...",
  "node_id": "7f3c9a01-...",
  "label": "Android Mama Wireguard"
}
```

- `connection_uuid` + `node_id` должны принадлежать этой подписке — иначе 404
  (`connection_not_found`), без уточнения, существует ли такая пара у кого-то
  ещё.
- `connection_uuid` здесь — **источник**: какой протокол/группу шерим.
  Создаваемый дочерний коннекшен получает собственный новый UUID.
- `label` — произвольная строка ≤ 64 символов, показывается владельцу в списке
  шеров; получателю — как имя сервера при импорте.
- Идемпотентность: повторный запрос на ту же тройку
  `(connection_uuid, node_id, label)` с живым токеном → вернуть существующий
  токен, не плодить дочерние коннекшены.
- Лимит: ≤ 20 активных токенов на подписку → 409 (`share_limit_reached`).

Ответ 200:

```json
{
  "share_token": "k7f29mxq4tvzabcd",
  "share_url": "frkn://conn/k7f2-9mxq-4tvz-abcd",
  "label": "Android Mama Wireguard",
  "created_at": "2026-08-24T12:00:00Z"
}
```

### 2. `POST /v1/config` — принимать share_token

`auth_data` получает альтернативную форму:

```json
{ "auth_data": { "share_token": "k7f29mxq4tvzabcd" }, "installation_uuid": "...", ... }
```

Семантика:

- Конфиг собирается **строго** для дочернего коннекшена токена на его ноде
  (join как обычно: клиентская часть connection + транспортная часть node).
  Поля `connection_id` / `node_id` в payload при share_token-авторизации
  игнорируются — по токену нельзя получить конфиг никакого другого коннекшена.
- Вся остальная механика без изменений: обмен WG/AWG-ключами (`public_key` в
  запросе), формат ответа, gzip+base64 контейнер. Нюанс: при импорте по
  токену клиент **не знает протокол заранее**, поэтому всегда генерирует
  WG-ключи и шлёт `public_key` — для не-WG протоколов бэк просто игнорирует
  это поле (просьба не валидировать строго лишние поля запроса).
- Токен отозван → 404 `share_not_found` (та же ошибка и при переборе, см.
  ниже).
- Подписка просрочена → стандартный expired-ответ `/v1/config` — клиент
  получателя покажет экран продления существующим флоу.
- **В ответе для share_token-авторизации дополнительно отдаём display-поля** —
  у получателя нет доступа к `/v1/services`, больше взять их неоткуда:

```json
{
  "share_label": "Android Mama Wireguard",
  "country_code": "FI",
  "country_name": "Finland",
  "service_type": "amnezia-premium",
  "service_protocol": "awg"
}
```

  `share_label` становится именем карточки сервера у получателя; страна и
  протокол — для иконки/флага и плашки протокола. `service_type` нужен, чтобы
  клиент классифицировал сервер как premium, а не self-hosted. Без этих полей
  карточка будет безымянной.

**Share token НЕ авторизует ничего, кроме `/v1/config`:** `/v1/services`,
`/v1/account_info`, `/v1/share*` с share_token → 403. Транзитивный минт
токенов токеном запрещён.

### 3. Дочерние коннекшены невидимы для владельца

Коннекшены с `issued_via: "share"`:

- **исключаются из `/v1/services`** — иначе приложение владельца увидит
  дубликаты своих серверов;
- **не считаются в `active_device_count`** в `/v1/account_info` (сейчас это
  conns.len()) — шаринг не должен раздувать счётчик «N out of 5».

Заметка про device limit: настоящего enforcement лимита устройств на
`/v1/config` сейчас нет (счётчик display-only). В v1 шаринга лимит для
получателей **не вводим** — это отдельная фича. Когда/если device-limit
появится, решим отдельно, едят ли шары слоты.

### 4. `POST /v1/shares` — список токенов подписки (владелец)

Auth: `api_key`. Ответ 200:

```json
{
  "shares": [
    {
      "share_token": "k7f29mxq4tvzabcd",
      "label": "Android Mama Wireguard",
      "node_id": "7f3c9a01-...",
      "created_at": "2026-08-24T12:00:00Z",
      "last_used_at": "2026-08-25T09:30:00Z"
    }
  ]
}
```

`last_used_at` — чтобы владелец видел, жив ли шар. Если дорого — можно
отложить, но revoke без списка бесполезен.

### 5. `POST /v1/share/revoke` — отозвать (владелец)

Auth: `api_key`. Тело: `{ "share_token": "..." }`.

- 200 — отозван: токен помечается revoked **и дочерний коннекшен удаляется**
  (существующий ZMQ delete → нода сносит пир/UUID). Доступ получателя
  прекращается фактически, а не только перевыдача. Дальнейшие `/v1/config` по
  токену → 404.
- 404 — не найден/уже отозван: клиент трактует как успех.

## Безопасность

- Rate-limiting: в api сейчас нет никакого — перенести RateLimiter из mrkting
  (per-IP + глобальный предохранитель, как у `/s/{code}`) на ветку
  share_token в `/v1/config` и на `/v1/share*`. На любой мусор — одинаковый
  404 `share_not_found`, промахи логируются с IP (всплеск = перебор).
- Токен не логируем в plaintext (тот же принцип, что для api_key).
- Ссылка `frkn://conn/` передаётся через мессенджеры — считаем токен
  компрометируемым; revoke дешёвый и всегда доступен в UI владельца.

## Edge cases

- **Нода выведена из эксплуатации**: `/v1/config` по токену → 404
  `node_not_found`; у получателя один сервер, `/v1/services` ему недоступен,
  поэтому клиент показывает «сервер недоступен, обратитесь к владельцу».
  Владельцу достаточно перевыпустить шар на новую ноду (старый токен при этом
  удаляется вместе с дочерним коннекшеном).
- **Смена IP ноды**: `node_id` тот же, токен продолжает работать, конфиг
  отдаёт новый IP — подхватывается обычным рефрешем получателя.
- **Смена страны**: неприменимо — у получателя нет выбора страны, коннекшен
  зафиксирован токеном.
- **Просрочка подписки владельца**: см. выше, стандартный expired-ответ.

## Nginx / деплой

Новых путей вне `/v1/` нет — если gateway уже проксирует `/v1/` целиком,
конфиг nginx не меняется (в отличие от short codes, где нужны были `/short` и
vhost `s.frkn.org`).

## Клиентская сторона (наша)

- Импорт: `frkn://conn/<token>` — парсер рядом с `frkn://sub/`
  (`ImportController`), роутинг диплинка на iOS/Android/desktop. Импортируется
  одна карточка сервера: имя = label из ответа, без селектора стран/окружений.
- Владелец: кнопка «Поделиться подключением» в карточке сервера →
  `/v1/share` → показ ссылки + QR. Список шеров с revoke — в Active Devices.
- Получатель: рефреш конфига — тот же `/v1/config` с `share_token`
  (существующий путь `updateServiceFromGateway`, меняется только наполнение
  `auth_data`).
