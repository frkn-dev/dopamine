# Proposal: config_rev — качать /v1/config только у изменившихся нод

## Зачем

Обновление списка серверов сейчас долгое. Клиент уже опрашивает
`GET /v1/catalog/version`. Хэш другой — он заново зовёт `POST /v1/config`
на **каждую** ноду из `/v1/services`, строго по одной. 30 нод — это десятки
секунд. Одна зависшая нода держит очередь до 45 секунд и ещё раз через
запасной API.

Имена и состав списка уже есть в `/v1/services`. Полный конфиг нужен только
новой ноде и ноде, у которой изменилась транспортная часть (адрес, порт,
ключи, junk, `node_ips`). Сейчас этого отличить нельзя, поэтому клиент
качает всё.

## Что уже есть

`GET /v1/catalog/version` — публичный GET, без шифрования шлюза. Клиент
читает:

```json
{ "response": { "version": "ab12…" } }
```

- пустой `version` — игнор;
- первый опрос после установки — запомнить хэш, список не перекачивать;
- хэш тот же — ничего не делать;
- хэш другой — полный рефреш подписки (`/v1/services` + `/v1/config` на все ноды).

Этот эндпойнт остаётся. Меняется только смысл «хэш другой»: после него
клиент сравнит ревизии и скачает конфиги выборочно.

## Изменение

### 1. `POST /v1/services` — `config_rev` в каждом коннекшене

Рядом с `node_id`, в `services[].connections[]`:

```json
{
  "connection_label": "Uncle Sam · AmneziaWG",
  "connection_uuid": "1ac65b82-...",
  "node_id": "7f3c9a01-...",
  "config_rev": "e3b0c44298fc1c14",
  "country_code": "US",
  "env": "production",
  "service_protocol": "awg"
}
```

`config_rev` — непрозрачная строка. Клиент сравнивает её на равенство и
ничего в ней не парсит. Рекомендация: hex SHA-256 (можно обрезать до 16
символов) от канонического JSON **серверной** части конфига этой ноды.

В хэш входит всё, что меняет уже выданный клиенту конфиг:

- адрес (`hostName` / endpoint) и порт;
- `node_ips`;
- серверные ключи (WG/AWG `server_pub_key`, preshared, Reality publicKey /
  shortId / serverName, параметры Hysteria);
- junk и AWG 3.1: Jc, Jmin, Jmax, S1–S4, H1–H4, I1–I5, HeaderProtectionKey;
- DNS, который зашит в конфиг.

В хэш не входит:

- клиентский ключ / UUID — его генерирует приложение и присылает само;
- `connection_label`, страна, `env`, `service_protocol` — они и так приходят
  в `/v1/services`, ради переименования `/v1/config` не нужен.

Требования:

- тот же `node_id` и тот же конфиг ноды → тот же `config_rev` у всех
  подписок;
- сменился IP при том же `node_id` (кейс Uncle Sam) → `config_rev` другой;
- поле отсутствует или пустое → старое поведение: клиент качает `/v1/config`
  для этой ноды всегда. Так можно выкатывать ноды по одной.

### 2. `GET /v1/catalog/version` — хэш должен двигаться вместе со списком

`version` меняется, когда выполняется любое из условий:

- у любой ноды, которая попадает в `/v1/services` онлайн-клиентам, сменился
  `config_rev`;
- нода добавлена в каталог или пропала из него (офлайн, дроп). Офлайн-нода
  по-прежнему не входит в `connections[]`.

`version` не меняется, если ни состав онлайн-нод, ни их `config_rev` не
менялись. Повторный GET без изменений инфраструктуры возвращает тот же хэш.

Формат ответа не меняется: `{ "response": { "version": "<string>" } }`.

Хэш каталога можно оставить глобальным, не per-подписка. Чужое изменение
разбудит лишний `POST /v1/services`, но не лишний `/v1/config`: ревизии
нод этой подписки совпадут, и конфиги не пойдут.

### 3. `POST /v1/config` — опционально вернуть тот же `config_rev`

```json
{
  "config": "<как сейчас>",
  "config_rev": "e3b0c44298fc1c14",
  "node_ips": ["…"],
  "api_config": {}
}
```

Клиент сохраняет ревизию из этого ответа, а не ту, что видел в
`/v1/services` до запроса. Если между двумя ответами нода успела
измениться, следующий опрос каталога не совпадёт и конфиг скачается ещё раз.

Поле аддитивное. Нет поля — клиент запоминает ревизию из `/v1/services`.

`connection_id`, `node_id`, обмен клиентским ключом — без изменений.

## Как клиент будет себя вести

После смены `version`:

1. Один `POST /v1/services`.
2. Ноды нет в ответе — карточка удаляется сразу, `/v1/config` не зовётся.
3. `node_id` новый или `config_rev` не равен сохранённому — `POST /v1/config`
   только для этой ноды.
4. `config_rev` тот же — карточка, адрес и ключи остаются как есть.
   Имя можно обновить из `connection_label` этого же ответа.
5. `config_rev` пустой — как сейчас, конфиг качается.

Первая установка качает все конфиги: сравнивать не с чем.

## Обратная совместимость

- Старые клиенты поле игнорируют и по-прежнему качают все конфиги, когда
  меняется хэш каталога.
- Нода без `config_rev` не ломает выборку: для неё конфиг качается всегда.
- `/v1/config` без поля в ответе остаётся валидным.

## Edge cases

- **Смена IP, тот же `node_id`.** `config_rev` другой, хэш каталога другой.
  Клиент зовёт `/v1/config` только для этой ноды и переписывает адрес.
- **Нода ушла в офлайн или дропнута.** Её нет в `connections[]`, хэш каталога
  другой. Клиент удаляет карточку и не запрашивает конфиг.
- **Только переименовали лейбл.** `config_rev` тот же. Если из-за лейбла
  хэш каталога тоже менять нечем — имя обновится при следующем реальном
  изменении каталога. Если лейбл должен обновляться сразу, его надо включить
  в хэш каталога, но не в `config_rev`.
- **Гонка.** `/v1/services` отдал rev=2, `/v1/config` собрался ещё на rev=1
  и вернул `"config_rev": "1"`. Клиент сохраняет `"1"`. Следующий опрос
  видит `"2"` и скачивает снова.
