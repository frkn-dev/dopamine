# Телеметрия блокировок: что собирать и как не утонуть в шуме

Задача: юзер пишет «не работает, айпи X, оператор такой-то» — и мы не знаем, это
блокировка у его оператора, заблокирована вся подсеть, нода легла или у человека
MTU/NAT. Нужно, чтобы приложение само собрало факты и прислало их нам, а мы
отличили блок от смерти ноды.

Старт — по кнопке (осознанное согласие + нет потока мусора), дальше автоматика на
ошибках подключения. Ниже: что именно даёт ответ, что уже есть в коде, схема
payload'а, серверная часть и честные ограничения по платформам.

## 1. Вопрос → данные

| Вопрос | Что нужно | Откуда берём |
|---|---|---|
| Какая нода и какой порт не открываются | `address`, `port`, `protocol`, `node_id` | конфиг коннекта в клиенте (`vpnconnection.cpp:414`, `m_remoteAddress`) / `/v1/config` |
| У кого именно не открывается | ASN оператора + страна/регион + наш собственный exit-IP юзера не нужен | серверная сторона по IP запроса (см. §6) |
| Блок или сеть в целом | пробы: ICMP, TCP connect, TLS-хендшейк, UDP-хендшейк WG/AWG | клиентская проба (§4) |
| Насколько массово | «сколько разных ASN пожаловались на этот адрес за час» | агрегат в API (§6) |
| Совпадает ли с нашей картиной | доступность того же адреса с нашего RU-полигона | `env/node-probe` (уже крутится каждые 20 мин с домашнего ISP) |
| Нода реально жива для других | heartbeat fnode + `status` ноды в API | ffcore `NodeResponse`, `src/score/` |

Ключевая мысль: **одно сообщение юзера ничего не доказывает**, доказательство
появляется при сопоставлении с независимой точкой (наш полигон) и с состоянием
ноды. Поэтому payload бесполезен без §5.

## 2. Что уже есть (опорные точки)

**Клиент (dopamine):**
- Коды ошибок — `client/core/defs.h:41-124`. Профильное: `ServerConnectionTimeoutError = 1300`
  (сейчас это единственный видимый юзеру признак «не подключилось»).
- Место, где фиксируется таймаут рукопожатия — `client/ui/controllers/connectionController.cpp:230`
  и `:1109` (ветка iOS/NE/Android).
- Адрес и порт сервера на руках к моменту коннекта: `client/vpnconnection.cpp:414`
  (`NetworkUtilities::getIPAddress(credentials.hostName)`), порт — из конфига контейнера.
- Транспортные классы для проб: в проекте уже есть `QTcpSocket`/`QSslSocket` (Qt6),
  UDP — `QUdpSocket`.
- API-слой: `client/ui/controllers/api/apiConfigsController.cpp` — `m_settings->getGatewayEndpoint() + "v1/..."`,
  авторизация через `auth_data` в теле (`:165`, `:518`). Туда же добавляется ручка отчёта.
- UI: страница поддержки `client/ui/qml/Pages2/PageSettingsApiSupport.qml` (Telegram/почта/сайт) —
  кнопка «Собрать данные и отправить» логично встаёт туда; рядом есть `supportTag`
  (`client/ui/models/api/apiDevicesModel.cpp:85`), который уже служит идентификатором устройства для поддержки.

**Сервер (ffcore):**
- Публичный инвентарь нод `GET /status` — адрес, порты, статус, страна (`src/bin/api/http/handlers/node.rs`).
- Модель ноды: `NodeResponse` — `address`, `inbounds`, `node_ips`, `country`, `type` (`src/memory/node.rs:109`).
- Скоринг нод `src/score/` (серии `node.score.*`, ручка `/v1/admin/nodes/score`) — готовое место,
  куда можно подмешать «долю заблокированных ASN» как ещё один сигнал.
- WS-метрики нод: `src/bin/api/http/handlers/metrics.rs` (heartbeat), т.е. «нода жива» уже известно.

**Внешние точки (уже есть):**
- `env/node-probe` — раз в 20 минут пробит все ноды из РФ-домашнего ISP (ICMP/TCP/UDP по каждому порту),
  пишет `latest.json`. Это ровно «контрольная группа» для сравнения.
- `env/vpn-sub-check` — реальный коннект через sing-box с проверкой трафика. Даёт ground truth
  «работает / не работает», но только по подписке и медленно.
- `frkn-docs/server-healthcheck-research.md` — уже посчитанная стоимость методов проб
  (TCP ↔ TLS ↔ WG-handshake ↔ QUIC).

## 3. Что отправлять (payload)

Минимум (кнопка сейчас):

```json
{
  "auth_data": { "subscription_id": "…" },
  "report": {
    "support_tag": "…",                       // идентификатор устройства, не секрет
    "app": { "version": "4.8.14.70", "platform": "windows", "os": "10.0.19045" },
    "target": { "node_id": "…", "address": "93.89.220.49", "port": 443,
                "protocol": "awg", "transport": "udp" },
    "error":  { "code": 1300, "stage": "handshake", "when": "2026-10-24T12:00:00Z" },
    "probe":  {
      "icmp": { "ok": true, "rtt_ms": 41 },
      "tcp":  [ { "port": 443, "state": "timeout", "ms": null },
                { "port": 8443, "state": "open", "ms": 38 } ],
      "udp":  [ { "port": 443, "state": "no-answer" } ],
      "dns":  { "host": "est1.frkn.org", "ips": ["93.89.220.49"] }
    },
    "device": { "splittunnel": true, "killswitch": true, "mtu": 1280 },
    "note": "текст юзера, опционально"
  }
}
```

Чего в payload **не** должно быть: приватных ключей, полного конфига, I1–I5/junk-параметров,
телефона/почты, IP юзера в открытом виде (он и так виден серверу по соединению, но в
тело его не кладём и в логи не пишем).

ASN/оператора клиент **не определяет** — это делает сервер по source IP (§6): не гоняем
IP юзера через сторонние geoip-сервисы и не зависим от того, что напишет человек.

## 4. Клиентская проба — что реально можно

Матрица (из `server-healthcheck-research.md`, проверено нашим опытом):

| Проба | Что доказывает | Стоимость |
|---|---|---|
| ICMP | хост жив; ICMP часто режут — «нет» ничего не доказывает | копейки |
| TCP connect к порту | SYN/SYN-ACK: адрес и порт доступны | копейки |
| TLS ClientHello с SNI | DPI не гасит TLS (для VLESS/Reality) | низкая |
| WG/AWG handshake initiation | сервер принимает именно наш протокол | средняя (нужна крипта; ключи из конфига уже есть) |
| QUIC Initial | hy2 живой | высокая (дни, лучше через sing-box/xray harness) |

Ограничения по платформам:
- **Windows/macOS**: пробу можно привязать к физическому интерфейсу (bind source IP), т.е.
  мерить «как видит провайдер», даже когда туннель поднят. Это главный кейс: юзер
  подключён к ноде A, а нода B у него блокируется.
- **iOS (NetworkExtension)**: привязать сокет к интерфейсу нельзя — проба уйдёт в туннель.
  Значит на iOS проба честна только когда VPN выключен, либо помечается «измерено через туннель».
- **Android**: то же ограничение через `VpnService` (bind к underlay делается через
  `Network.bindSocket` — можно, но только для сокетов, созданных в приложении, и это надо проверять).

Практический вывод для MVP: проба = ICMP + TCP по всем портам ноды + (позже) WG-handshake.
Этого достаточно, чтобы отличить «порт закрыт/молчит» от «порт открыт».

## 5. Блок vs «нода легла» — матрица выводов

| Клиент | Наш полигон (RU-ISP) | Heartbeat ноды | Вывод |
|---|---|---|---|
| fail | fail | ok | блок у конкретного оператора/региона |
| fail | fail | fail | нода/датацентр недоступны целиком |
| fail | ok | ok | локальная проблема юзера: MTU, NAT, фаервол, сплит-туннель |
| fail | ok | fail | нода умерла, блокировки нет |
| ok | fail | ok | заблокирован наш полигон (или у него сломался ISP), нода жива |

Именно эта таблица — то, ради чего вообще собираем данные. Без независимой точки
(полигон) отчёт юзера отвечает только «у меня не работает».

Дополнительно: **UDP-сигнатура DPI**. «TCP 443 открыт, UDP 443 молчит у всех юзеров
одного ASN» — классическая картина блокировки QUIC/AWG, при живой TCP-части. Один
такой паттерн на 3+ независимых ASN = блок на маршруте, а не у оператора.

## 6. Серверная часть

Эндпоинт: `POST /v1/report/block`, авторизация как у остальных `/v1/*` (`auth_data`),
rate limit: 1 отчёт на `(support_tag, node_id, port)` в час, глобально 30/час на подписку.

Приём:
1. Валидация `auth_data` → `subscription_id`.
2. ASN и страна по source IP: локальная база (MaxMind GeoLite2 ASN) или кэшируемый
   вызов к ipinfo/ip-api **с сервера**, без передачи IP юзера наружу в открытом виде.
   В БД кладём `asn`, `asn_name`, `country`, `region` — сам IP юзера не храним.
3. Запись в `block_reports` (партиционирование по дням, retention 90 дней).

Агрегация (раз в 5 минут, materialized view / периодический job):
- `(node_address, port, protocol, asn, hour) → count, unique_support_tags`
- `(node_address, port) → distinct_asn_count` за час — главный сигнал массовости.
- алерт в Telegram, когда `distinct_asn_count >= 3` и наш полигон по этому адресу тоже
  fail (иначе — «локальная проблема юзера»).

Отдача:
- `GET /v1/admin/blocks` — таблица для дашборда/поддержки (фильтры: нода, ASN, час).
- проброс в скоринг: `block_ratio` как ещё один компонент `node.score.*`
  (сейчас там load/users/bw/reliability/uptime — `src/score/mod.rs`).

## 7. Приватность

- Кнопка = явное согласие; текст кнопки прямо говорит, что уходит.
- Храним: `subscription_id`, `support_tag`, ASN/страна/регион, адрес ноды, результат проб,
  версия/платформа. Не храним: IP юзера, ключи, содержимое конфига, переписку.
- Retention 90 дней для сырых отчётов, агрегаты — бессрочно (это обезличенные счётчики).
- Отчёт не должен содержать ничего, что юзер не ожидает: перед отправкой показываем
  превью payload'а (он короткий и читаемый).

## 8. MVP (кнопка) — что делать по шагам

1. **Клиент, проба** (`client/core/` — маленький класс `BlockProbe`): ICMP (через `QProcess ping`
   или сырой сокет на десктопе), TCP connect с таймаутом 3 с по каждому порту ноды,
   UDP-проба «answered/closed/no-answer», резолв hostname. Всё параллельно, общий таймаут 6 с.
2. **Клиент, UI**: кнопка в «Поддержка» (`PageSettingsApiSupport.qml`) — «Проверить соединение
   с сервером и отправить отчёт»; после пробы показываем превью и «Отправить».
3. **Клиент, API**: `POST v1/report/block` через существующий слой (`apiConfigsController`).
4. **ffcore**: таблица + ручка + ASN-lookup + агрегат + алерт. Ручка для админки.
5. **Проверка**: поднять на боксе искусственную блокировку (заблокировать IP ноды в local
   firewall) и убедиться, что отчёт приходит, агрегат считает, алерт срабатывает,
   а полигон в это время видит ноду живой (то есть отчёт помечен «локальная проблема»).

Оценка: клиент (десктоп) — 1.5–2 дня, API+БД+алерт — 1–1.5 дня, Android/iOS — +1–2 дня
на платформенные ограничения bind. Это research-оценка, не обязательство.

## 9. Фазы 2 и 3

- **Фаза 2 — автоматика на ошибке**: при `ErrorCode::1300` (и «подключено, но трафик не идёт»)
  автоматически собрать пробу и отправить без кнопки, с сэмплированием (не чаще 1/час на
  пару нода+порт). Юзеру — ненавязчивая строка «отчёт отправлен».
- **Фаза 2.5 — WG/AWG handshake-проба** (см. `server-healthcheck-research.md` §Фаза 2):
  единственный честный способ сказать «UDP-порт принимает наш протокол», а не «молчит».
  Крипта уже есть в Go-либе; на Python её тоже можно реализовать (~150 строк, X25519 +
  ChaCha20-Poly1305 + BLAKE2s) — так уже сделан пробер для полигона.
- **Фаза 3 — активный мониторинг**: полигон расширяется на 2–3 оператора РФ, данные
  стыкуются с отчётами юзеров, ноды с подтверждённой блокировкой автоматически
  помечаются и выводятся из выдачи для затронутых ASN (сейчас выдача общая).

## 10. Риски и антипаттерны

- **Не верить одному отчёту.** Один юзер с кривым MTU выглядит как блокировка.
- **Не собирать «всё подряд в фоне»** без сэмплирования: это и приватность, и батарея.
- **Не считать «UDP не ответил» за блокировку** — AWG/WG/H2 молчат на мусор по дизайну.
- **Не отправлять IP юзера в сторонние geoip-сервисы** — ASN считаем на своей стороне.
- **Не смешивать «блок» и «нода перегружена»**: перегруз видна по `node.score` и метрикам,
  блок — по совокупности ASN.
