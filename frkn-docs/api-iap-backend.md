# Backend Tasks — App Store IAP + Attribution

Scope for the backend team: attribution in `/account`, purchase binding &
verification for App Store IAP, App Store Server Notifications, and metrics.
Derived from the client code (`client/ui/controllers/api/apiConfigsController.cpp`).

Products (auto-renewable subscriptions, one subscription group in ASC):

| Product ID | Duration |
|---|---|
| `frkn_premium_1_month` | 1 month |
| `frkn_premium_3_month` | 3 months |
| `frkn_premium_6_month` | 6 months |
| `frkn_premium_12_month` | 12 months |

Environments: TestFlight purchases arrive as **Sandbox** transactions and the
client routes them to the **DEV gateway**; production purchases go to the PROD
gateway with `environment = Production`. Keep both pipelines.

## 1. `POST /account` — attribution fields

Extend the existing public endpoint (see the account/trial spec) with optional
attribution fields. All other behavior (dedup, welcome email, limits) unchanged.

Request (all fields shown; new ones marked **new**):

```json
{
  "trial": true,
  "email": "user@example.com",
  "language": "ru",
  "referred_by": "ABC123",
  "marketing_emails": true,
  "system_notifications": true,
  "os": "ios",
  "app_version": "4.8.14.5",
  "installation_uuid": "3F6C9E2A-....-...."
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `os` | string | no (**new**) | `ios`, `macos`, `windows`, `linux`, `android` (Qt `QSysInfo::productType()`) |
| `app_version` | string | no (**new**) | e.g. `4.8.14.5` |
| `installation_uuid` | string (UUID) | no (**new**) | Anonymous install id generated by the client. Stable per install; use it to link trial → later purchases from the same install. |

Response — unchanged:

```json
{ "subscription_id": "c6831dad-...", "ref_code": "f7a0353fbdbc", "message": "Account created", "email_sent": true }
```

Also accept the same three fields on the `POST /account` upsert variant
(`{"subscription_id": ...}`) so attribution can be backfilled.

Storage: persist all three on the account row + write a `trial_created` event
with the full attribution payload (needed for metrics, §4).

## 2. `POST /v1/subscriptions` — purchase binding & verification

Existing AGW-envelope endpoint (same encrypted transport as `/v1/account_info`,
see the AGW envelope spec). Already called by the client after a purchase and
on restore; this task is the **verification + duration logic**, plus a new
`product_id` field the client will start sending.

Decrypted request payload (exact keys as sent by the client):

```json
{
  "os_version": "ios",
  "app_version": "4.8.14.5",
  "language": "ru",
  "installation_uuid": "3F6C9E2A-....",
  "user_country_code": "DE",
  "service_type": "amnezia-premium",
  "service_protocol": "awg",
  "transaction_id": "2000000123456789",
  "product_id": "frkn_premium_3_month"
}
```

| Field | Presence | Notes |
|---|---|---|
| `transaction_id` | always | Apple's **originalTransactionId** (stable across renewals of one subscription). This is the subscription's primary key on our side. |
| `product_id` | always for new clients; absent from old builds | One of the 4 ids above. Cross-check with Apple, never trust blindly. |
| `service_type` | always | `amnezia-premium` for IAP. |
| `installation_uuid`, `language`, `os_version`, `app_version` | always | Attribution, link to the trial account if present. |
| `user_country_code`, `service_protocol` | optional | |

Server-side flow:

1. Verify the transaction with **App Store Server API**:
   `GET /inApps/v1/transactions/{transactionId}` and/or
   `GET /inApps/v1/subscriptions/{originalTransactionId}` (statuses of all
   auto-renewable subscriptions of this customer).
   - Decode `signedTransactionInfo` (JWS) and validate the certificate chain
     against the **Apple Root CA – G3**. Do not skip chain validation.
   - Extract: `productId`, `originalTransactionId`, `expiresDate`,
     `environment`, `purchaseDate`.
   - Check `environment` matches the gateway the request hit
     (Sandbox → DEV, Production → PROD).
2. If `product_id` is present, require it to equal Apple's `productId`.
3. Upsert `iap_subscriptions` keyed by `originalTransactionId` with
   `product_id`, `status`, `expires_at = expiresDate`, `auto_renew = true`,
   `environment`, and link to the account (`installation_uuid` if available).
4. Respond with the VPN configuration for the premium service — **same
   response format the endpoint returns today** (consumed by
   `importServiceFromBilling` on the client). Response must be sent through the
   AGW envelope (AES with the request keys).
5. **Idempotency**: the same `transaction_id` sent again (restore flow,
   reinstalls) must return the current config without duplicating anything.
   The client iterates all restored transactions and calls this endpoint per
   transaction — handle bursts gracefully.

Errors: `4xx` if the transaction does not verify / belongs to a different app
bundle id / mismatched environment. The client shows a generic purchase error
popup in these cases.

## 3. App Store Server Notifications V2 endpoint

Apple pushes subscription lifecycle events to a URL you configure in
App Store Connect (App → App Information → App Store Server Notifications;
separate **Production** and **Sandbox** URLs — point Sandbox at DEV).

```
POST https://api.frkn.org/apple/assn        (production)
POST https://<dev-host>/apple/assn          (sandbox)
```

Request body:

```json
{ "signedPayload": "<JWS>" }
```

Processing:

1. Decode the JWS **without trusting it**, then validate the x5c certificate
   chain against Apple Root CA – G3 and the expected `bundleId` / `environment`.
2. Payload fields: `notificationType`, `subtype`, `notificationUUID`
   (dedup key), `data.signedTransactionInfo` (nested JWS — same verification),
   `data.environment`.
3. Update `iap_subscriptions` accordingly.

Notification types to handle:

| notificationType / subtype | Action |
|---|---|
| `SUBSCRIBED` | New subscription (also arrives via §2 bind — keep idempotent) |
| `DID_RENEW` | Extend `expires_at` from signedTransactionInfo |
| `DID_CHANGE_RENEWAL_STATUS` / `AUTO_RENEW_DISABLED` | `auto_renew = false` (churn intent) |
| `DID_CHANGE_RENEWAL_STATUS` / `AUTO_RENEW_ENABLED` | `auto_renew = true` |
| `EXPIRED` | `status = expired`, revoke/flag config after grace |
| `GRACE_PERIOD` | `status = grace` |
| `BILLING_RETRY` | `status = billing_retry` |
| `REFUND` | `status = refunded`, revoke access |
| `REVOKE` | Family-sharing revoke → revoke access |
| `PRICE_INCREASE` / `RENEWAL_EXTENSION` / `OFFER_REDEEMED` | Log event, update state |

Rules:

- Always respond `200` after successful validation (Apple retries otherwise);
  `4xx` only for invalid signatures.
- Deduplicate by `notificationUUID`; make every handler idempotent.
- Store the raw payload in `iap_events` for audit/debug.

## 4. Metrics & dashboard data

Store these events (table `events` or per-type tables):

- `trial_created` — subscription_id, os, app_version, installation_uuid,
  language, referred_by, timestamp
- `iap_bound` — original_transaction_id, product_id, environment,
  installation_uuid, timestamp
- `iap_renewed`, `iap_expired`, `iap_refunded`, `iap_auto_renew_off` —
  from ASSN

Suggested schema:

```
accounts(subscription_id PK, email, created_at, os, app_version,
         installation_uuid, referred_by, language)
iap_subscriptions(original_transaction_id PK, product_id, status,
                  auto_renew bool, environment, expires_at,
                  account_id FK NULL, installation_uuid NULL)
iap_events(id PK, original_transaction_id, transaction_id,
           notification_uuid UNIQUE, type, subtype, payload jsonb, created_at)
```

KPIs to expose:

- Trials per day, split by os / app_version / referred_by
- Trial → paid conversion (accounts with an `iap_subscriptions` row /
  `trial_created` count)
- Purchases per product_id (1/3/6/12 months mix)
- Renewal rate, churn (`auto_renew = false` share), refunds
- Revenue estimate by product price tier × active subscriptions

## 5. Apple-side setup required (coordinates with app owner)

- App Store Connect → Agreements, Tax, Banking: Paid Applications active.
- 4 subscription products created in one subscription group (ids above).
- App Store Server API key (ASC → Users and Access → Integrations →
  In-App Purchase) for the verification calls in §2.
- ASSN V2 URLs configured (Production + Sandbox) pointing at §3 endpoints.
