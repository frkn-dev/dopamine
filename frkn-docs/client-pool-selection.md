# Как клиент выбирает пул → ноду → адрес

Документ описывает ровно то, что делает Dopamine при нажатии Connect: из чего
складывается список кандидатов, как учитываются веса адресов, где участвует
пинг, и что происходит при сбоях. Код: `connectionController.cpp`
(`connectToServerIndex`, `retryWithNextIp`), `servers_model.cpp`
(`weightForNodeIp`, `portForNodeIp`, `endpointHealth`).

---

## 1. Три уровня, которые нельзя путать

| Уровень | Что это | Кто выбирает |
|---|---|---|
| **Строка (карточка)** | запись подписки: протокол + нода/пул | **пользователь** (тап в списке/карточке) |
| **Пул** | все адреса строки (`node_ips`) | сервер/бэкенд (какие адреса вообще есть) |
| **Адрес** | конкретный `IP:port` из пула | **алгоритм** (веса + пинг) |

Правило №0: **выбор пользователя главнее любого алгоритма.** Выключенный
тумблером адрес не участвует никогда — ни с весом 100, ни как «последний
шанс». Если выключены все адреса строки — подключение не начинается, а
возвращается ошибка `ServerConnectionTimeoutError` с текстом
«All addresses are turned off».

---

## 2. Откуда берутся адреса и их свойства

Для выбранной строки клиент собирает список `PoolEntry`:

```
PoolEntry { row, ip, port, weight }
```

- `ip` — элемент `node_ips`. У одиночной ноды без `node_ips` остаётся пустой
  `ip`: дозвон идёт по `hostName` строки (это CDN-фронт или единственный адрес).
- `port` — `node_ports[ip]`, иначе порт протокола строки
  (`containers[].<protocol>.port`). Один адрес пула может слушать свой порт.
- `weight` — `node_weights[ip]`, иначе **100**.

Правила веса (важно для совместимости):

- карта `node_weights` приходит с бэкенда вместе с `node_ports`; ключи всегда
  совпадают с `node_ips`;
- **дефолт 100**, если ключа нет;
- **0 или отрицательное значение = «вес не задан» → 100.** Нода старой сборки
  присылает `0` вместо отсутствия поля, и трактовать это как «вес ноль»
  означало бы никогда не подключаться к такой ноде;
- легаси-поле `weight` верхнего уровня (максимум по адресам) клиент **не
  использует** — оно существует только чтобы старые клиенты не выбрасывали
  сервер целиком.

Для примера из тредa — пул из двух нод по два адреса:

```
NODE1: 93.89.220.48 w=75, 93.89.220.49 w=75
NODE2: 77.221.152.88 w=25, 77.221.152.89 w=25
```

Σw = 200, значит суммарно NODE1 получает 150/200 = **75 %** подключений,
NODE2 — **25 %**. Внутри ноды веса адресов равны, поэтому конкретный IP
решает пинг (см. §4).

## 3. Шаг 1 — отбрасываем то, что не может работать

Перед любым выбором пул фильтруется по трём причинам, в этом порядке:

1. **Выключено пользователем** (`Conf.poolDisabledEndpoints`, тумблеры в
   карточке). Выключенный адрес исключается полностью.
2. **Дубликаты.** Если один и тот же IP встречается в нескольких строках пула,
   он учитывается один раз (первая строка владеет им).
3. **Проба сказала «нет рукопожатия»** — адрес с *свежим* (моложе 5 минут)
   вердиктом `unreachable` уходит во **второй круг** (`m_ipFallbackPool`):
   сначала пробуем живые, и только если ни один не поднялся — возвращаемся к
   отброшенным. Проба может ошибаться (не тот порт, старый кэш, сеть моргнула),
   а живой адрес пользователю нужнее нашей уверенности.

Если после фильтра не осталось ни одного адреса — ошибка, подключение не
начинается.

---

## 4. Шаг 2 — вес + пинг как вето

Среди выживших адресов считается выбор. Ключевое: **пинг не множитель веса, а
фильтр.** Вес отвечает за «насколько нода надёжная/ёмкая», пинг — за «можно ли
вообще этим адресом пользоваться прямо сейчас».

Алгоритм:

1. Для каждого адреса берётся последний RTT из кэша замеров (TTL 5 минут).
2. Вычисляется `minRtt` — минимум по тем адресам, у которых замер есть.
3. **Вето по задержке:** адрес выбывает, если
   `rtt > minRtt + 150 мс` **и одновременно** `rtt > 200 мс`
   (`kPingVetoDeltaMs = 150`, `kPingVetoAbsoluteMs = 200`).
   Двойное условие нужно, чтобы не выбрасывать нормальные адреса в пуле, где
   все медленные (например, мобильная сеть 180/210 мс): там разница важнее
   абсолютного числа.
4. Адреса **без замеров** (никогда не мерили) не выбывают — они участвуют по
   весу. Это прямое требование: нет данных — просто пробуем, успех подключения
   и есть проверка.
5. **Взвешенный случайный выбор:** `P(ip) = w / Σw` по оставшимся. Именно
   случайный, а не «максимальный вес»: иначе весь трафик всегда шёл бы в одну
   ноду, а вес нужен для распределения нагрузки.
6. Если после вето не осталось никого (бывает, когда все адреса медленные и
   один сильно хуже) — берём исходный список целиком и всё равно выбираем по
   весам. Отказ от подключения хуже, чем подключение к медленному адресу.

Порядок остальных адресов в пуле (для повторных попыток) — по убыванию веса.
Выбранный адрес всегда первый.

### Память о рабочем адресе

`Conf.lastConnectedEndpoint` — адрес, на котором в прошлый раз реально
поднялось соединение. Он ставится первым **только если веса всех живых
кандидатов равны**. Если веса разные, память игнорируется: иначе она
полностью отменяла бы веса (всегда один и тот же IP).

## 5. Шаг 3 — попытки и ошибки

Порядок попыток: выбранный адрес → остальные по весу → адреса из второго круга
(отброшенные пробой).

Таймауты одной попытки:

| Режим | Таймаут |
|---|---|
| обычный | 20 с (`kManualConnectTimeoutMs`) |
| «плохая сеть» (сработал 7-секундный сторож) | 8 с (`kBypassAttemptTimeoutMs`) |

Переход к следующему адресу происходит, когда:

- истёк таймаут попытки;
- платформа сообщила ошибку старта туннеля;
- соединение поднялось, но за 8 с (десктоп) / 30 с (iOS, Android) не пришло
  ни одного байта — «Connected без трафика» не считается успехом.

Если не поднялось ничего и включён `reconnect until cancelled`, клиент уходит в
цикл ожидания сети (3 → 5 → 10 → 20 → 30 с) и повторяет всё заново.

---

## 6. Сторож 7 секунд (плохая сеть)

Отдельно от выбора адреса существует сторож на **7 секунд** от момента Connect:

- если висит `Preparing` (валидация конфига через api) — валидация бросается,
  идём по сохранённому конфигу;
- если висит предконнектная проба или автовыбор — они отменяются;
- дальше клиент перебирает адреса по очереди с таймаутом 8 с.

Сторож **не трогает уже идущий дозвон**: иначе он рвал бы нормальную попытку
каждые 7 секунд (так и было в одной из сборок — приложение вообще не
подключалось).

---

## 7. Откуда берутся пинги (и почему им нельзя верить на туннеле)

Замеры делает `HealthCheckController`: настоящий handshake (WG/AWG — UDP-пакет
с junk-параметрами I1–I5, VLESS — TCP, Hysteria2 — полный путь через xray).

Ограничения:

- пробы **запрещены при поднятом туннеле**: трафик уходит внутрь VPN, и
  «сервер не отвечает» означало бы «не отвечает туннель». Вердикты, снятые
  через туннель, стираются при отключении;
- кэш живёт 5 минут; свежесть считается по каждому адресу отдельно;
- общего «не чаще раза в минуту» больше нет — оно блокировало пробы для
  адресов, по которым замера не было вовсе (карточка висела на `no data`);
  остался только троттлинг 30 с от повторных запусков.

Что видит пользователь в карточке:

| Состояние | Подпись |
|---|---|
| замер есть, свежий | `65 ms · available` (или `· in use`) |
| замер есть, старше 5 мин | `65 ms · cached` |
| мерили, ответа не было | `unreachable` / `unreachable · cached` |
| не мерили никогда | `not measured yet` |
| идёт проверка | `checking… · 65 ms last` / `checking… · —` |
| туннель поднят, адрес не активный | `not checked — VPN is on` |

## 7.5. Фаза 2 — загрузка ноды (load), ждёт api

Согласовано с бэкендом, клиентская часть ещё не подключена (нет ручки).
Пропоузал: `frkn-docs/api-node-load-proposal.md`.

**Контракт:** отдельный `POST /v1/nodes/load` (`auth_data` + до 50 `node_ids`),
ответ `{ "at": ISO, "load": { "<node_id>": 0.0…1.0 } }`. Отдельная ручка, а не
поле в `/v1/config`: конфиг тянется раз в 3 часа и умеет зависать, а нагрузка
нужна на момент подключения.

**Формула:** `w_eff = max(w × (1 − load), w × 0.15)`,
`P(ip) = w_eff / Σw_eff`. Пол 15 % — чтобы один кривой score не выбрасывал ноду
из пула целиком.

**Правила клиента:**

- запрос в момент подготовки подключения, ожидание максимум 800 мс;
  не успели — решаем по весам, подключение не тормозим;
- кэш ответа 30 с (реконнекты не дёргают ручку), данные старше 60 с
  игнорируются;
- нет ключа для ноды = данных нет, вес не корректируется (нельзя трактовать
  «нет нагрузки» как 0.0 — это перетянуло бы весь трафик);
- 404/таймаут — тихий откат к весам, без ошибок пользователю.

**Порядок приоритетов (финальный):** выбор пользователя → выключенные адреса →
провал пробы (вето) → вето по пингу (150/200 мс) → вес × загрузка → взвешенный
рандром.

## 8. Логи для проверки

При подключении в лог пишется одна строка решения:

```
[IPPOOL] ping veto: 77.221.152.89 260 ms vs best 34 ms (weight 25)
[IPPOOL] pick 93.89.220.48 weight 75 p=0.375 rtt 34 (candidates 4, weighted 3)
[IPPOOL] created pool with 4 entries for row 58 fallback 0
```

`p` — вероятность, с которой этот адрес был выбран из живых. По этим строкам
видно: сработало вето или нет, какие веса пришли, сколько кандидатов осталось.

## 9. Частые вопросы

**Почему не «всегда самый большой вес»?** Тогда вторая нода пула простаивала бы
всегда, а пул существует именно для распределения. 75/25 — это доли, не
приоритет.

**Почему пинг не умножает вес?** Умножение смешивает две разные вещи: вес — это
свойство ноды (канал, ёмкость, стабильность), пинг — свойство текущего момента.
При умножении нода с весом 75 и плохим пингом проигрывала бы ноде с весом 25,
и вес перестал бы значить то, что в него заложено.

**Что если у всех адресов вес 100?** Поведение как раньше: фактически решает
пинг (вето) и случайный выбор среди живых.

**Что если бэкенд не присылает `node_weights`?** Все адреса получают 100 —
пул ведёт себя как однородный.

**Что если пользователь выключил адрес с весом 100?** Он не участвует. Остальные
перенормируются: их доли считаются от новой суммы весов.
