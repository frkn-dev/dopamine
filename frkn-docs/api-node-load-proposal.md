# Пропоузал: скоринг загрузки ноды для клиента (node load)

Статус: **предложение к api**. Клиентская часть готова к приёму, реализуется
после появления ручки.

## Зачем

Веса (`node_weights`) описывают, **сколько нода должна брать в норме**. Они
статичны: нода с весом 75 продолжает получать 75 % подключений пула, даже если
её канал уже забит. Клиент не видит нагрузку и не может её учесть.

Нужен один числовой score на ноду, который api отдаёт по запросу, — клиент
умножает на него вес. Управление остаётся на бэкенде: меняется score — меняется
распределение, без выката клиента.

## Контракт

```http
POST /v1/nodes/load
Content-Type: application/json

{
  "auth_data": { "id": "<subscription id>", "api_key": "…" },
  "node_ids": ["1edded35-c900-4f4a-804a-d087c97a46b8", "…"]
}
```

```jsonc
200 OK
{
  "at": "2026-11-05T12:40:10Z",
  "load": {
    "1edded35-c900-4f4a-804a-d087c97a46b8": 0.82,
    "a9c1…": 0.31
  }
}
```

Правила:

- `load` — **доля занятости, 0.0 … 1.0** (1.0 = полностью загружена). Не
  проценты и не «сколько осталось».
- Нода без данных (только что поднялась, метрик нет) — **ключа нет** в ответе.
  Не присылать `0.0` «по умолчанию»: ноль читается как «свободна» и перетянет
  на себя весь трафик.
- `at` — время, на которое посчитан score. Клиент отбрасывает данные старше
  **60 секунд**.
- Ответ маленький: только id и число. Никаких имён, адресов, тегов.

Коды: `200` — ок (возможно частично, по подмножеству), `400` — невалидный
запрос, `401` — нет auth, `404` — ручки нет (старый api; клиент молча работает
по весам).

## Как считать score

Источник данных уже есть: fnode шлёт метрики в `metrics.reciever`, у api есть
`MetricStorage`. Ничего нового собирать не нужно, нужен агрегат.

Рекомендуемая формула (загрузка — это **канал**, а не CPU):

```
bandwidth_util = tx_bps / max_bandwidth_bps      // из метрик ноды
conn_util      = active_conns / conn_capacity    // conn_capacity — конфиг ноды
cpu_util       = cpu_percent / 100

load = clamp(max(bandwidth_util, 0.6*conn_util + 0.4*cpu_util), 0.0, 1.0)
```

Смысл: канал — жёсткое узкое место, поэтому он берётся как есть; соединения и
CPU влияют мягче (весами 0.6/0.4), потому что сами по себе не означают
деградацию.

Сглаживание обязательно: отдавать **скользящее среднее за 60 с**, а не
мгновенное значение. Иначе score дёргается и клиенты начинают «мигрировать»
туда-сюда.

## Ограничения и защита

- **Rate limit**: 1 запрос на установку не чаще раза в 15 секунд (клиент и так
  кэширует 30 с; лимит нужен от чужого кода).
- **Не более 50 node_ids за запрос.** Клиенту больше не нужно: он спрашивает
  только ноды текущего пула (обычно 2–5).
- Порог «перегружена» рекомендую ставить в конфиге api (например 0.85), чтобы
  при желании можно было **не отдавать** score выше порога, а сразу писать 1.0
  — это жёстче и понятнее, чем тонкая настройка на клиенте.

## Как это использует клиент

```
w_eff = max(w × (1 − load), w × 0.15)
P(ip) = w_eff / Σ w_eff
```

- пол 15 % — нода не обнуляется никогда, иначе один кривой score выкидывает её
  из пула полностью;
- данные старше 60 с или отсутствующие id — вес не корректируется;
- запрос уходит при подготовке подключения, ждём максимум **800 мс**;
  не успели — подключаемся по весам, ничего не блокируется;
- приоритеты остаются: выбор пользователя → выключенные адреса → провал
  пробы (вето) → вето по пингу → вес × загрузка → взвешенный рандом.

Пример: пул `75 / 25`, у ноды с весом 75 `load = 0.8` →
`w_eff = 75×0.2 = 15` и `25×1.0 = 25` → перегруженная нода получает 37 % вместо
75 %. Ровно то, что нужно: без правки весов и без выката клиента.

## Совместимость

- Ручка аддитивная; старые клиенты её не вызывают — для них ничего не меняется.
- Новый клиент со старым api: `404` → работа по весам, как сейчас.
- Ноды без метрик: ключа нет → их вес не корректируется.
